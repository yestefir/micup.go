### B. Discovered Issues

**P2 — Cancelled IDENTIFY waits extend other shards' cooldowns.** In `src/shard/limiter.go`, `wait` advanced `next` before its timer/context select. Cancellation returned an error but left that future reservation behind. Even a context already cancelled at entry extended the schedule. `NewManager` retains the same shared limiter through session callbacks, so abandoned reservations can also delay later runs of the same manager.

Evidence: `TestCancelledIdentifyWaitsDoNotDelayLaterShards` seeds an existing cooldown one hour ahead, configures the normal five-second interval and performs four cancelled calls. One case cancels before entry; the other observes entry into the cancellable wait before cancelling each call. Before the fix, both cases report: `four cancelled waits added 20s to later shards' cooldown`. The test does not sleep for an hour or claim a measured 20-second runtime delay. After the fix both preserve the exact seeded deadline. A separate test holds admission busy and verifies another context can cancel without starting a cooldown.

**Resolved.** A cancellable per-manager gate serializes admission through the existing cooldown. After waiting, context is checked again; only a successful admission sets the next deadline. Already admitted calls retain their interval, even if their callers later stop. No production occurrence or end-to-end restart latency was measured.

### F. Regression & Risk Assessment

All deadline state is owned by the admission gate. Waiting for that gate and the cooldown both respect context; the final context recheck prevents a ready timer from admitting an already-ended context. Previous successful admissions keep their cooldown; the fix does not reset pacing on manager restart or reclaim calls that might already identify. No strict shard ordering or end-to-end frame-spacing guarantee is introduced because dialing/scheduling happen after admission. Holding admission through the cooldown avoids waking every waiter to compete on each interval. This requires a channel per manager's limiter, with measured extra allocation and slower constructor timings. It does not change the previously fixed per-connection Gateway write gate or active-write timeout. No new regression required a revert.
