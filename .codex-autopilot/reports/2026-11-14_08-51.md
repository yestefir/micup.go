### B. Discovered Issues

**P2 — Multipart layout assumptions produce wrong routing or premature data side effects.** `src/rest/attachments.go` iterated the server array and used `part_number` only in error text. A reversed plan `[2,1]` assigned the first four bytes to part 2 and the final two to part 1. Count mismatches were checked only after some data was read/uploaded. Duplicate, zero, negative and gapped numbering were not checked.

The [official upstream Fluxer upload guide](https://docs.fluxer.com/topics/uploads/) describes 1-based part identifiers and fixed part sizes apart from the final segment. **Inference:** file segments should be matched by logical part number, rather than relying on unspecified response-list ordering. No claim is made that a real Micup instance currently returns reversed plans; sorting is defensive normalization of numbered plans.

Observed baseline evidence for source `abcdef`, size 6, part size 4:

| Fixture | Before | After |
|---|---|---|
| Reversed `[2,1]` | Part 1 received `ef`, part 2 `abcd`; fixture completed | Part 1 receives `abcd`, part 2 `ef` |
| Too few `[1]` | Read 4 bytes, 1 PUT, then error | Error before reads/data PUTs |
| Too many `[1,2,3]` | Read 6 bytes, 2 PUTs, then error | Error before reads/data PUTs |
| Duplicate/zero/negative/gapped numbers | Each read 6 bytes, sent 2 PUTs and completed under permissive fixture | Each errors before reads/data PUTs |
| Zero part size/no parts | Already rejected without file/data side effects | Same |

**Resolved.** This demonstrates client behavior against synthetic plans, not a production corruption incident. Tiny fixture sizes intentionally exercise the same byte-layout logic without a 10 MiB workload; they do not model the real API's multipart selection threshold. A strict real storage service might reject a mis-sized part rather than complete it.
